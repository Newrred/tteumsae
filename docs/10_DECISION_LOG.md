## 2026-08-28 — 감사 후 제품·구현 우선순위 재정렬

상태: 확정

결정:

- `00_START_HERE`, `03_FEATURE_MATRIX`, `04_SCREEN_FLOWS`는 현재 구현 사실만 기록한다.
- 제품 목표는 `01_PRODUCT_AND_SCOPE`, 이 결정 기록과 최신 도착 마감 스펙을 기준으로 한다.
- 신규 시간 계약은 상대 `deadlineMinutes`가 아니라 절대
  `arrivalDeadlineEpochMillis`를 보낸다. 서버가 수신시각 기준으로 남은 시간을 내림
  계산해 네트워크 지연이 마감을 뒤로 미루지 않게 한다.
- 관심 조건은 별도 필수 단계가 아니라 선택 필터로 둔다.
- 첫 알파는 경유지 한 곳만 완료 흐름으로 제공한다. 제품상 최대 2곳 원칙은 유지하되,
  두 번째 장소는 한 곳 흐름의 실제 성과를 확인한 뒤 실험한다.
- TourAPI 전체 보강보다 운영시간 신뢰의 얇은 기준선과 도착 마감 핵심 플로우를 먼저 완료한다.
- `TteumsaeApp.kt`는 전면 재작성하지 않고 새 경로 기능부터
  `RouteFlowViewModel + SavedStateHandle`과 화면별 파일로 분리한다.

이유:

- 현재 Android는 도착 시각 없이 내부 24시간 예산을 사용하므로 새 제품 가치를 검증하지 못한다.
- 최대 5곳, 필수 조건 단계와 평균 머무름은 `늦지 않게 한 곳 들르기`라는 핵심 판단을 흐린다.
- 상대 분 올림은 15분 경계와 느린 요청에서 안전하지 않다.
- 운영 DB의 운영시간 보유율이 0.9%라 장소 수 확대보다 추천 신뢰를 먼저 확보해야 한다.
- 일반 경로 주변 추천은 기존 지도·내비 서비스와 직접 경쟁하므로 최대 체류시간과 출발
  권장시각이 첫 화면에서 드러나야 한다.

영향:

- 2026-08-26 스펙은 절대 마감·1곳 알파 기준으로 개정한다.
- 기존 `2026-08-26-deadline-aware-route-core.md` 구현 계획은 새 계획이 작성될 때까지 중지한다.
- 이전 `경유지 n/5`, 5곳 선택과 별도 필수 CONDITIONS를 신규 UI에 계승하지 않는다.
- 고정 출발 알림은 1차에 유지하고 지오펜스·두 번째 장소·원격 저장 동기화는 검증 후로 미룬다.

다시 검토할 조건:

- 한 곳 추천의 이해율, 선택률, 외부 내비 실행률과 거짓 가능 판정률이 알파 기준을 통과할 때
  두 번째 장소를 별도 실험한다.
- 운영시간·주차·대기 데이터가 쌓이면 공통 최소 15분에 장소별 내부 의미 체류시간을 추가한다.

상태: 확정

결정:

- 지도 핀에는 추가 이동시간만 표시하고 장소 선택 후 최대 체류시간과 출발 마감 시각을 표시한다.
- 기본 경유지는 한 곳이며 실제 가능한 경우에만 두 번째 장소를 약하게 제안한다.
- 제품상 경유지는 최대 2곳이다.
- 고정 출발 알림을 기본으로 하고 위치 기반 도착 감지·재계산은 선택 기능으로 둔다.
- 실제 주행은 외부 카카오맵이 담당하며 틈새는 이동 상태의 지속 추적을 약속하지 않는다.

이유:

- 세 곳 이상은 약속 시간 보호보다 일정 계획에 가까워져 현재 서비스 목적과 맞지 않는다.
- 외부 내비 사용 중 우리 앱이 실제 이동을 확실하게 알 수 없으므로 고정 알림이 더 신뢰할 수 있는 기본값이다.

영향:

- 활성 Android는 내부 `extraTimeMinutes=1,440` 대신 실제 남은 전체 시간인 `deadlineMinutes`를 사용한다.
- 신규 시간 모델은 서버 호환 분기로 추가하고 구버전 요청은 유지한다.
- 2026-08-16의 제품상 최대 5곳 결정은 최대 2곳으로 대체한다. 서버와 Kakao 전달 계층의 5곳 호환은 유지할 수 있다.
- 기존 `평균 머무름`과 미리 합산한 체류시간 표시는 제거 대상이다.

다시 검토할 조건:

- 사용자 검증에서 두 번째 경유지 이용률과 완료율이 충분히 높을 때만 세 곳 이상을 별도 일정 계획 기능으로 검토한다.
- 백그라운드 위치 권한 심사와 개인정보 고지가 준비되지 않으면 도착 감지는 출시하지 않고 고정 알림만 유지한다.

## 2026-08-28 — Gate 1-B 데이터·운영 신뢰 경계

상태: 확정

결정:

- Kakao Mobility는 KST 일일 7,000건부터 경고하고 8,000건에서 외부 호출 전에 차단한다.
- 공급자 호출 예약·성공·쿼터·5xx·timeout은 좌표와 사용자 식별자 없이 일별 집계한다.
- 운영시간을 완전히 해석하지 못하면 `OPEN`이 아니라 `UNKNOWN`으로 남긴다.
- 축제는 KST 예정 방문일이 완전한 시작일·종료일 범위 안일 때만 추천한다.
- TourAPI 원문과 수동 검수를 분리하고 `place_curations`가 `effective_places`에서 우선한다.
- 첫 운영 검수 범위는 강릉 활성 장소 100곳이며 근거 없는 값은 추정하지 않는다.
- 공개 health 계약은 유지하고 상세 운영 집계는 `CRON_SECRET` 인증 경로로 분리한다.

이유:

- 무료 Kakao 쿼터를 요청 처리 중 뒤늦게 발견하면 핵심 경로 기능 전체가 갑자기 멈춘다.
- 영업정보가 없거나 복잡한 장소를 열림으로 추정하는 것이 후보 수 부족보다 더 큰 신뢰 손상이다.
- 전체 TourAPI 원문을 사람이 덮어쓰면 다음 동기화에서 근거와 수정 이력이 사라진다.
- 전국 전체 보강보다 실제 알파 지역의 얇고 검증 가능한 기준선이 Gate 2 판단에 유용하다.

영향:

- 예산·검수·운영 집계는 migration 006과 service-role 전용 RPC를 통해 관리한다.
- 예산/쿼터 소진은 503과 `Retry-After`로 반환하고 직선거리 대체 경로를 만들지 않는다.
- 복잡한 운영시간은 추천에 남을 수 있지만 `UNKNOWN`으로 명시되며 닫힘을 확정하지 않는다.
- 강릉 100곳 검수 확장은 Gate 3의 무결과율과 선택률을 확인한 뒤 결정한다.

다시 검토할 조건:

- Kakao 계약 쿼터나 유료 플랜이 바뀔 때 경고·차단선을 재산정한다.
- 운영시간 원문 패턴별 실제 오판 데이터가 쌓이면 파서 범위를 테스트와 함께 확장한다.

- 자동차 추천의 실제 Kakao Mobility 후보 호출은 최대 8개로 제한한다.

이유:

- Hobby Cron은 같은 시각대 안에서 최대 ±59분 오차가 있어 분 단위 순서에 의존할 수 없다.
- 현재 Vercel Function 제한은 60초지만 외부 요청과 DB 작업에 timeout이 없어 플랫폼
  강제 종료 전에 상태를 저장한다는 보장이 없다.
- 무료 운영에서 후보 20개 경로 호출은 비용·지연 대비 검증 가치가 낮다.

다시 검토할 조건:

- 유료 Vercel로 전환해 분 단위 Cron·긴 Function 또는 durable workflow를 사용할 때.
- Gate 3 실제 경로 검증에서 후보 8개로 인한 의미 있는 추천 누락이 확인될 때.
